An **Ansible playbook** in networking is a YAML file that describes **what network devices should do**, in a repeatable and automated way. Instead of logging into each router or switch manually, you define the desired configuration once, and Ansible applies it across many devices.

## Why use Ansible for networking?

Imagine you have:

- 10 routers
    
- 50 switches
    
- 20 firewalls
    

If you need to change the DNS server, create VLANs, or update NTP settings, doing it manually is slow and error-prone. Ansible automates these tasks.

---

## How Ansible works in networking

```
               +----------------------+
               |   Ansible Control    |
               |      Machine         |
               +----------+-----------+
                          |
               SSH / API / NETCONF
                          |
      -----------------------------------------
      |             |             |            |
   Router1       Switch1      Switch2     Firewall
```

The control machine runs the playbook and connects to network devices using:

- SSH (most common)
    
- NETCONF
    
- REST APIs
    
- Vendor-specific APIs
    

No agent needs to be installed on the devices.

---

## Components of a networking playbook

### 1. Inventory

This lists the network devices.

```ini
[routers]
R1 ansible_host=192.168.1.1
R2 ansible_host=192.168.1.2

[switches]
SW1 ansible_host=192.168.1.10
SW2 ansible_host=192.168.1.11
```

---

### 2. Playbook

Example:

```yaml
---
- name: Configure NTP on Cisco routers
  hosts: routers
  gather_facts: no

  tasks:

    - name: Configure NTP Server
      cisco.ios.ios_config:
        lines:
          - ntp server 10.10.10.1
```

This means:

- Run on all routers.
    
- Don't collect Linux facts (`gather_facts: no`).
    
- Send the command:
    

```
ntp server 10.10.10.1
```

to every router.

---

## Example 1: Configure VLANs

Suppose 30 switches need VLAN 100.

Manual CLI:

```
Switch(config)# vlan 100
Switch(config-vlan)# name SALES
```

Playbook:

```yaml
---
- name: Create VLAN
  hosts: switches
  gather_facts: no

  tasks:

    - name: Configure VLAN 100
      cisco.ios.ios_config:
        lines:
          - vlan 100
          - name SALES
```

Run once:

```
ansible-playbook vlan.yml
```

All switches receive the configuration.

---

## Example 2: Configure interface description

Instead of manually configuring:

```
interface GigabitEthernet0/1
description Connected to Server
```

Playbook:

```yaml
---
- name: Configure Interface
  hosts: routers

  tasks:

    - name: Set description
      cisco.ios.ios_config:
        parents: interface GigabitEthernet0/1
        lines:
          - description Connected to Server
```

The `parents` section tells Ansible to enter interface configuration mode before applying the command.

---

## Example 3: Configure OSPF

Instead of logging into every router:

```
router ospf 1
 network 10.0.0.0 0.0.0.255 area 0
```

Playbook:

```yaml
---
- name: Configure OSPF
  hosts: routers

  tasks:

    - name: Enable OSPF
      cisco.ios.ios_config:
        parents: router ospf 1
        lines:
          - network 10.0.0.0 0.0.0.255 area 0
```

---

## Example 4: Backup configurations

One of the most common networking use cases.

```yaml
---
- name: Backup Router Configurations
  hosts: routers

  tasks:

    - name: Backup running configuration
      cisco.ios.ios_config:
        backup: yes
```

Ansible saves each router's running configuration to the control machine.

---

## Example 5: Gather device information

Instead of checking each router manually:

```
show version
```

Use:

```yaml
---
- name: Collect Device Facts
  hosts: routers

  tasks:

    - name: Gather facts
      cisco.ios.ios_facts:
```

Ansible collects information such as:

- Hostname
    
- Model
    
- Serial number
    
- IOS version
    
- Interfaces
    

---

## Example 6: Verify configuration

Suppose you want to check whether OSPF neighbors are up.

```yaml
---
- name: Verify OSPF
  hosts: routers

  tasks:

    - name: Show OSPF Neighbors
      cisco.ios.ios_command:
        commands:
          - show ip ospf neighbor
```

This runs the show command and returns the output without changing the configuration.

## Idempotency

A key feature of Ansible is **idempotency**. If the desired configuration already exists, Ansible reports that no change is needed.

For example:

Playbook:

```yaml
- vlan 100
```

If VLAN 100 is already present:

```
ok=1
changed=0
```

If it doesn't exist:

```
ok=1
changed=1
```

This allows you to run the same playbook multiple times safely.

|`cisco.ios.ios_config`|Push configuration commands|
|`cisco.ios.ios_command`|Execute show/operational commands|
|`cisco.ios.ios_facts`|Gather device facts|
|`arista.eos.eos_config`|Configure Arista EOS devices|
|`junipernetworks.junos.junos_config`|Configure Juniper Junos devices|
|`ansible.netcommon.netconf`|Interact with devices over NETCONF|

## End-to-end example

```yaml
---
- name: Configure Campus Routers
  hosts: routers
  gather_facts: no

  tasks:

    - name: Configure hostname
      cisco.ios.ios_config:
        lines:
          - hostname Branch1

    - name: Configure NTP
      cisco.ios.ios_config:
        lines:
          - ntp server 10.10.10.1

    - name: Configure interface
      cisco.ios.ios_config:
        parents: interface GigabitEthernet0/1
        lines:
          - description Uplink
          - no shutdown

    - name: Save configuration
      cisco.ios.ios_config:
        save_when: modified
```

### What this playbook does

1. Connects to all routers in the `routers` inventory group.
    
2. Changes the hostname to `Branch1`.
    
3. Configures the NTP server.
    
4. Enters interface `GigabitEthernet0/1`, sets a description, and ensures it is enabled.
    
5. Saves the running configuration only if changes were made.
    

In practice, network teams use playbooks like this to standardize configurations, deploy changes across dozens or hundreds of devices, back up configurations, verify network state, and reduce the risk of configuration drift. The same approach works across different vendors by using the appropriate Ansible collection and modules for each platform.

# Ansible Playbook Notes – Running Show Commands on Cisco IOS Devices

## Objective

This playbook connects to Cisco IOS routers and executes the **`show version`** command. Since it is only collecting information, no configuration changes are made.

---

# Playbook

```yaml
---
- name: Run show commands on ciscoIOS
  hosts: ciscoIOS
  gather_facts: False

  tasks:
    - name: Run show commands
      cisco.ios.ios_command:
        commands:
          - show version
      register: cisco_show_version

    - name: Display cisco_show_version
      ansible.builtin.debug:
        var: cisco_show_version
```

---

# Line-by-Line Explanation

## Play Name

```yaml
- name: Run show commands on ciscoIOS
```

- Descriptive name of the play.
    
- Displayed when the playbook runs.
    

Output:

```
PLAY [Run show commands on ciscoIOS]
```

---

## Hosts

```yaml
hosts: ciscoIOS
```

- Specifies the inventory group on which the playbook will run.
    
- Every device under the `ciscoIOS` inventory group will execute the tasks.
    

Example Inventory

```ini
[ciscoIOS]
R1
R2
```

Result:

```
R1
R2
```

both execute the playbook.

---

## gather_facts

```yaml
gather_facts: False
```

### Purpose

Disables automatic fact collection.

Normally, Ansible gathers Linux server facts like:

- CPU
    
- Memory
    
- OS Version
    
- Disk Usage
    

using the **setup** module.

For Cisco routers, these Linux facts are not applicable.

Setting:

```yaml
gather_facts: False
```

- Speeds up execution.
    
- Avoids unnecessary operations.
    

---

# Task 1

```yaml
- name: Run show commands
```

A descriptive name for the task.

Displayed as:

```
TASK [Run show commands]
```

---

## ios_command Module

```yaml
cisco.ios.ios_command:
```

This module is used to execute **operational (show) commands** on Cisco IOS devices.

Examples:

- show version
    
- show ip interface brief
    
- show running-config
    
- show inventory
    
- show vlan
    

It **does not modify** device configuration.

---

## commands

```yaml
commands:
  - show version
```

This list contains CLI commands to execute.

You can specify multiple commands:

```yaml
commands:
  - show version
  - show ip interface brief
  - show inventory
```

Ansible executes them in the given order.

---

## register

```yaml
register: cisco_show_version
```

### Purpose

Stores the module output in a variable.

Without `register`:

- Output is displayed during execution but cannot be reused.
    

With `register`:

```yaml
register: cisco_show_version
```

The output becomes available for later tasks.

Think of `register` as creating a variable:

```
show version output
            ↓
cisco_show_version
```

---

# Task 2

```yaml
- name: Display cisco_show_version
```

Uses the Debug module to display the stored variable.

---

## Debug Module

```yaml
ansible.builtin.debug:
```

Prints variables or messages to the terminal.

Examples:

```yaml
debug:
  msg: Hello
```

or

```yaml
debug:
  var: hostname
```

---

## var

```yaml
var: cisco_show_version
```

Displays the complete contents of the registered variable.

Output includes:

- stdout
    
- stdout_lines
    
- changed
    
- warnings
    
- failed
    
- deprecations
    

---

# Understanding the Output

## changed

```yaml
changed: false
```

Meaning:

No configuration changes were made.

Reason:

The `show version` command is read-only.

---

## failed

```yaml
failed: false
```

Meaning:

The command executed successfully.

---

## stdout

```yaml
stdout:
```

Contains the raw command output as a single string.

Example:

```
Cisco IOS Software...
Version 15.2(4)S5...
```

Useful when storing or parsing raw output.

---

## stdout_lines

```yaml
stdout_lines:
```

Contains the same output split into a list of lines.

Example:

```yaml
stdout_lines:
  - Cisco IOS Software
  - Version 15.2
  - R1 uptime is 26 minutes
```

This format is easier to process in loops or conditional logic.

---

## warnings

```yaml
warnings:
```

Example:

```
ansible-pylibssh not installed,
falling back to paramiko
```

Meaning:

- Ansible attempted to use the faster `pylibssh` library.
    
- Since it wasn't installed, it used `paramiko` instead.
    
- The playbook still ran successfully.
    

---

## deprecations

These messages indicate that some underlying modules or APIs are using features that will be removed in future versions of Ansible.

Example:

```
Importing to_bytes is deprecated
```

This does **not** affect your playbook directly. It is mainly informational for developers and maintainers of Ansible collections.

# PLAY RECAP Explained

```
PLAY RECAP

R1 : ok=2 changed=0 failed=0
R2 : ok=2 changed=0 failed=0
```

Meaning:

- **ok=2** → Both tasks completed successfully (`Run show commands` and `Display cisco_show_version`).
    
- **changed=0** → No configuration changes were made.
    
- **failed=0** → No task failures occurred.
    
- **unreachable=0** → All devices were reachable.
    
- **skipped=0** → No tasks were skipped.

# Key Takeaways

- `hosts` specifies which inventory group the play runs on.
    
- `gather_facts: False` skips unnecessary fact collection for network devices.
    
- `cisco.ios.ios_command` executes operational (`show`) commands without changing device configuration.
    
- `commands` accepts one or more CLI commands to execute.
    
- `register` stores the module output in a variable for later use.
    
- `ansible.builtin.debug` displays the contents of variables.
    
- `stdout` contains the raw command output as a string.
    
- `stdout_lines` contains the output split into individual lines, making it easier to process.
    
- `changed: false` confirms the playbook only gathered information and did not modify the devices.
    
- The **PLAY RECAP** provides a quick summary of task results across all targeted devices.
