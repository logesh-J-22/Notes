The key idea is that **Ansible needs a structured way to know what devices exist and how to connect to them**. YAML provides that structure in a format that's both easy for humans to read and easy for Ansible to parse.

## Why do we use YAML for inventory?

Imagine you have 100 routers.

Without an inventory, Ansible has no idea:

- Which routers exist.
    
- What their IP addresses are.
    
- What credentials to use.
    
- Which routers belong to the branch, data center, or core network.
    

The inventory is simply a **list of devices and their connection details**.

YAML is used because it:

- Is easy to read.
    
- Supports nested data (groups and subgroups).
    
- Supports variables.
    
- Is less error-prone than custom formats.
    

---

## Think of the inventory as a contact list

Suppose you have three routers:

|Router Name|Management IP|Location|
|---|---|---|
|R1|192.168.1.10|Bangalore|
|R2|192.168.1.11|Chennai|
|R3|192.168.1.12|Hyderabad|

In your notebook, you might write:

```text
Router Name    IP Address
R1             192.168.1.10
R2             192.168.1.11
R3             192.168.1.12
```

In Ansible, you store the same information in YAML.

```yaml
all:
  hosts:
    R1:
      ansible_host: 192.168.1.10

    R2:
      ansible_host: 192.168.1.11

    R3:
      ansible_host: 192.168.1.12
```

This is simply a structured version of your notebook.

# How are routers stored in YAML? 

Let's look at the file one level at a time.

```yaml
all:
```

`all` is the top-level group. Every host belongs to this group.

Inside it:

```yaml
all:
  hosts:
```

`hosts` tells Ansible that the following entries are devices it can connect to.

Now define a router:

```yaml
R1:
```

`R1` is the inventory name (also called the host alias). It doesn't have to match the router's hostname. It's just the name Ansible uses.

Under `R1`, specify the management IP:

```yaml
R1:
  ansible_host: 192.168.1.10
```

This tells Ansible:

> "When I say `R1`, connect to `192.168.1.10`."

---

## Adding more connection information

A network device usually needs more than just an IP address.

```yaml
all:
  hosts:

    R1:
      ansible_host: 192.168.1.10
      ansible_user: admin
      ansible_password: Cisco123
      ansible_network_os: ios
      ansible_connection: network_cli
```

Here's what each field means:

|Field|Purpose|
|---|---|
|`ansible_host`|Management IP address|
|`ansible_user`|Login username|
|`ansible_password`|Login password|
|`ansible_network_os`|Network operating system (for example, Cisco IOS)|
|`ansible_connection`|Connection type (`network_cli` for SSH to network devices)|

When Ansible runs, it effectively does something like:

```text
Connect to 192.168.1.10
Username: admin
Password: Cisco123
Use Cisco IOS modules
```

# Grouping routers

Suppose your network has:

```text
Data Center
    DC-R1
    DC-R2

Branch Office
    BR-R1
    BR-R2
```

In YAML:

```yaml
all:
  children:

    datacenter:
      hosts:
        DC-R1:
          ansible_host: 10.10.10.1

        DC-R2:
          ansible_host: 10.10.10.2

    branch:
      hosts:
        BR-R1:
          ansible_host: 172.16.1.1

        BR-R2:
          ansible_host: 172.16.1.2
```

Here:

- `children` defines groups.
    
- `datacenter` and `branch` are group names.
    
- Each group contains its own routers.
    

If your playbook says:

```yaml
hosts: branch
```

Ansible automatically runs the tasks on `BR-R1` and `BR-R2`.

## What happens when you run a playbook?

Suppose the inventory contains:

```yaml
all:
  hosts:

    R1:
      ansible_host: 192.168.1.10

    R2:
      ansible_host: 192.168.1.11
```

And your playbook contains:

```yaml
- hosts: R1

  tasks:
    - name: Show version
      cisco.ios.ios_command:
        commands:
          - show version
```

Ansible reads the inventory and interprets it like this:

1. Find the host named `R1`.
    
2. Look up its IP address (`192.168.1.10`).
    
3. Connect to that router.
    
4. Run `show version`.
    
5. Return the output.
    

---

## Why not just use a list of IP addresses?

Imagine this inventory:

```text
192.168.1.10
192.168.1.11
192.168.1.12
```

It doesn't tell you:

- Which router is which.
    
- Which routers are in the branch office.
    
- Which credentials to use.
    
- Which operating system each device runs.
    

With YAML, you can associate all of that information with each device.

```yaml
R1:
  ansible_host: 192.168.1.10
  site: Bangalore
  role: Core
  ansible_network_os: ios
```

This makes the inventory much more useful than a simple IP list.

### Summary

The inventory file is like a directory of your network devices. YAML is used because it lets you organize routers into groups, attach connection details and variables to each router, and represent relationships through indentation. When Ansible starts a playbook, it first reads this inventory, determines which routers match the `hosts` field in the playbook, retrieves their connection information, connects to them, and then executes the requested tasks. This separation of **device information (inventory)** from **automation logic (playbooks)** is one of Ansible's core design principles.
