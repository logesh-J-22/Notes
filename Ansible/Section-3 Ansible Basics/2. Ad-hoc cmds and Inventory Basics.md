### Ad-hoc commands:

**Ad-hoc commands** are **one-time Ansible commands** that execute a single task on one or more managed hosts **without requiring a playbook**.

They're useful for quick administrative tasks, testing connectivity, gathering information, or making simple configuration changes.

## General syntax

```
ansible <host-pattern> -m <module> -a "<module-arguments>"
```

Where:

- `<host-pattern>`: The host or group from your inventory (for example, `all`, `routers`, or `switches`).
- `-m`: Specifies the **module** to run.
- `-a`: Provides arguments to that module.

---

## Example 1: Test connectivity

For Linux hosts:

```
ansible all -m ping
```

The `ping` module checks whether Ansible can communicate with the managed hosts. It does **not** send an ICMP ping.

---

## Example 2: Run a command

```
ansible all -m command -a "hostname"
```

This runs the `hostname` command on every host.
## Example 3: Run a show version

```
ansible all -m cisco.ios.ios_command -a "commands='show version'"
```

- `-u` specifies the SSH username.
- `-k` (or `--ask-pass`) tells Ansible to **prompt you interactively** for the SSH password instead of reading it from the inventory or an extra variable.

For example:

```
ansible all \
  -m cisco.ios.ios_command \
  -a "commands='show version'" \
  -u admin \
  -k \
  -c ansible.netcommon.network_cli \
  -e ansible_network_os=cisco.ios.ios
```

When you run this, you'll see:

```
SSH password:
```

Type the password, and Ansible will use it for all hosts.

#### If the device requires enable mode

If you need to enter privileged EXEC mode (`#` prompt), use:

```
ansible all \
  -m cisco.ios.ios_command \
  -a "commands='show version'" \
  -u admin \
  -k \
  -b \
  -K \
  -c ansible.netcommon.network_cli \
  -e ansible_network_os=cisco.ios.ios
```

Here:

- `-b` enables privilege escalation (`become`).
- `-K` prompts for the become (enable) password.

#### Why did `ansible_password` work?

In your earlier command, you used:

```
-e ansible_password="admin"
```

That sets the `ansible_password` variable directly. It's equivalent to having:

```
ansible_user=admin
ansible_password=admin
```

in your inventory.

# Ansible Inventory Concept (Using Your Cisco IOS Example)

## 1. What is an Inventory in Ansible?

An **inventory** is a file where Ansible keeps information about the devices it manages.

It tells Ansible:

- **Which devices (hosts) to manage**
    
- **How to connect to those devices**
    
- **What credentials to use**
    
- **What type of operating system the devices run**
    
- **Which devices belong to which groups**
    

In your example, the inventory file is:

```ini
inventory_basic.ini
```

It contains information about two Cisco routers:

```ini
[ciscoIOS]
192.168.75.11
192.168.76.12
```

This tells Ansible:

> "I have two Cisco IOS devices that I want to manage."

---

# 2. Inventory Structure

A basic Ansible inventory has three main concepts:

```
Inventory
│
├── Groups
│     │
│     └── Hosts
│
└── Variables
```

Your inventory:

```ini
[ciscoIOS]
192.168.75.11
192.168.76.12

[all:vars]
ansible_connection=ansible.netcommon.network_cli
ansible_network_os=cisco.ios.ios
ansible_become=true
ansible_become_agent=enable
ansible_user=admin
ansible_password=admin
```

can be divided into:

1. Host group
    
2. Hosts
    
3. Variables
    

---

# 3. Host Groups

Your inventory has a group:

```ini
[ciscoIOS]
```

A group is a collection of devices with something in common.

Example:

```
ciscoIOS
   |
   +---- 192.168.75.11
   |
   +---- 192.168.76.12
```

Now instead of writing commands for each router individually, you can target the group:

```bash
ansible ciscoIOS -m cisco.ios.ios_command -a "commands='show version'"
```

Ansible will execute the command on both routers.

---

# 4. Hosts

Hosts are the actual devices managed by Ansible.

Your hosts:

```ini
[ciscoIOS]
192.168.75.11
192.168.76.12
```

Here:

```
192.168.75.11
        |
        +---- Cisco Router R1


192.168.76.12
        |
        +---- Cisco Router R3
```

A host can be identified by:

- IP address
    
- DNS name
    
- Hostname
    

Example:

```ini
[ciscoIOS]
R1 ansible_host=192.168.75.11
R3 ansible_host=192.168.76.12
```

Then you can use:

```bash
ansible R1 -m cisco.ios.ios_command -a "commands='show version'"
```

# 5. Inventory Variables

Variables define how Ansible communicates with devices.

Your variables:

```ini
[all:vars]
ansible_connection=ansible.netcommon.network_cli
ansible_network_os=cisco.ios.ios
ansible_become=true
ansible_become_agent=enable
ansible_user=admin
ansible_password=admin
```

---

## ansible_connection

```ini
ansible_connection=ansible.netcommon.network_cli
```

Defines the connection method.

For normal Linux servers:

```
ssh
```

For network devices:

```
network_cli
```

Your flow:

```
Ansible
   |
   | network_cli
   |
   SSH
   |
Cisco IOS Router
```

---

## ansible_network_os

```ini
ansible_network_os=cisco.ios.ios
```

Tells Ansible the device operating system.

Example:

Cisco IOS:

```ini
ansible_network_os=cisco.ios.ios
```

Cisco NX-OS:

```ini
ansible_network_os=cisco.nxos.nxos
```

Juniper Junos:

```ini
ansible_network_os=junipernetworks.junos.junos
```

This helps Ansible choose the correct commands and connection behavior.

---

## ansible_user

```ini
ansible_user=admin
```

The SSH username.

Equivalent to:

```bash
ssh admin@192.168.75.11
```

---

## ansible_password

```ini
ansible_password=admin
```

The SSH password.

Equivalent to:

```bash
ssh admin@192.168.75.11
Password: admin
```

For production environments, this should be stored using **Ansible Vault**, not plain text.

---

## Privilege Escalation Variables

Cisco devices have two common modes:

User EXEC:

```
Router>
```

Privileged EXEC:

```
Router#
```

To enter privileged mode:

```
Router> enable
Router#
```

Your inventory:

```ini
ansible_become=true
```

means:

> Enable privilege escalation.

---

```ini
ansible_become_agent=enable
```

means:

> Use Cisco's enable command.

Flow:

```
SSH Login

Router>
    |
    | enable
    |
Router#
```

# 6. Why `[all:vars]`?

Your variables are under:

```ini
[all:vars]
```

This means:

> Apply these variables to every device in the inventory.

Example:

```
all
 |
 +-- ciscoIOS
       |
       +--192.168.75.11
       |
       +--192.168.76.12
```

Variables apply everywhere:

```
192.168.75.11
    |
    + ansible_user=admin


192.168.76.12
    |
    + ansible_user=admin
```

---

# 7. Group-Specific Variables

Instead of:

```ini
[all:vars]
```

You can use:

```ini
[ciscoIOS:vars]
ansible_connection=ansible.netcommon.network_cli
ansible_network_os=cisco.ios.ios
ansible_user=admin
ansible_password=admin
```

Now only Cisco devices get these settings.

Example:

```
[ciscoIOS]
192.168.75.11
192.168.76.12

[linux]
192.168.10.20


[ciscoIOS:vars]
ansible_network_os=cisco.ios.ios


[linux:vars]
ansible_network_os=linux
```

# 8. How Ansible Uses Your Inventory

When you run:

```bash
ansible all \
-i inventory_basic.ini \
-m cisco.ios.ios_command \
-a "commands='show ip interface brief'"
```

The process is:

```
1. Read inventory_basic.ini

        |
        v

2. Find hosts

        |
        v

192.168.75.11
192.168.76.12

        |
        v

3. Read variables

        |
        v

network_cli
Cisco IOS
username/password

        |
        v

4. Connect using SSH

        |
        v

5. Execute:

show ip interface brief

        |
        v

6. Return output
```

# 9. Recommended Inventory Format for Your Lab

A cleaner version of your inventory:

```ini
[ciscoIOS]
R1 ansible_host=192.168.75.11
R3 ansible_host=192.168.76.12


[ciscoIOS:vars]
ansible_connection=ansible.netcommon.network_cli
ansible_network_os=cisco.ios.ios
ansible_user=admin
ansible_password=admin
ansible_become=true
ansible_become_method=enable
ansible_become_password=admin
```

Advantages:

- Easier to remember device names (`R1`, `R3`)
    
- IP addresses can change without changing commands
    
- Variables are organized by device type
