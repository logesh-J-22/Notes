# Ansible `cisco.ios.ios_hostname` State Options

## 📌 Overview

The `state` parameter in the `cisco.ios.ios_hostname` module defines **how Ansible should manage the hostname configuration** on a Cisco IOS device.

Syntax:

```yaml
cisco.ios.ios_hostname:
  config:
    hostname: CSR1
  state: <state_option>
```

The available states are:

|State|Purpose|
|---|---|
|`merged`|Add or update the hostname configuration.|
|`replaced`|Replace the existing hostname configuration with the desired hostname.|
|`overridden`|Remove existing hostname configuration and enforce the desired hostname.|
|`deleted`|Remove the hostname configuration.|

---

# 1. `state: merged`

## Purpose

`merged` ensures that the hostname defined in the playbook exists on the device.

It is the most commonly used state.

Example:

```yaml
cisco.ios.ios_hostname:
  config:
    hostname: CSR1
  state: merged
```

---

### Current Device

```text

```

```text

```

Desired configuration:

```yaml
hostname: CSR1
```

Ansible changes:

```text
hostname CSR1
```

Result:

```text
CSR1#
```

Output:

```yaml
changed: true
```

---

## Scenario 2: Hostname Already Exists

Current device:

```text
CSR1#
```

Desired:

```yaml
hostname: CSR1
```

Result:

```yaml

```

No command is sent because the desired state already exists.

# 2. `state: replaced`

## Purpose

`replaced` replaces the existing hostname configuration with the hostname defined in the playbook.

Example:

```yaml
cisco.ios.ios_hostname:
  config:
    hostname: EDGE-R1
  state: replaced
```

---

## Scenario

Current device:

```text
hostname R1
```

Desired:

```text
hostname EDGE-R1
```

Ansible replaces:

```diff
- hostname R1
+ hostname EDGE-R1
```

Result:

```text
EDGE-R1#
```

---

## Difference Between `merged` and `replaced`

For hostname management, both normally produce the same result because Cisco IOS allows only **one hostname**.

Example:

```text
hostname R1
```

Changing to:

```text
hostname CSR1
```

requires replacement.

However, the difference becomes more visible with modules that manage multiple configuration items.

Example:

Existing:

```text
interface GigabitEthernet0/1
 description USER
 ip address 10.1.1.1
```

Desired:

```text
description SERVER
```

With `merged`:

```text
description SERVER
ip address 10.1.1.1
```

Existing settings remain.

With `replaced`:

```text
description SERVER
```

Existing managed configuration can be replaced.

---

# 3. `state: overridden`

## Purpose

`overridden` makes the device configuration exactly match the desired configuration.

Any existing configuration managed by the module but not defined in the playbook is removed.

Example:

```yaml
cisco.ios.ios_hostname:
  config:
    hostname: CSR1
  state: overridden
```

---

## Scenario

Current device:

```text
hostname OLD-R1
```

Desired:

```text
hostname CSR1
```

Ansible enforces:

```diff
- hostname OLD-R1
+ hostname CSR1
```

Result:

```text
CSR1#
```

---

## Difference from `replaced`

|State|Behavior|
|---|---|
|`replaced`|Replace the existing configuration with the provided configuration.|
|`overridden`|Force the device to match the provided configuration exactly.|

`overridden` is more aggressive.

It is commonly used for compliance automation.

---

# 4. `state: deleted`

## Purpose

`deleted` removes the hostname configuration.

Example:

```yaml

  state: deleted
```


```yaml

```

Ansible removes the hostname configuration.

Equivalent CLI:

```text

```

---

## Result

Device returns to the default hostname:

```text

```

# Ansible Resource Module States: `rendered`, `gathered`, and `parsed`

## 📌 Overview

Ansible network resource modules support additional states that are used for **configuration conversion and information gathering**.

These states are mainly used for:

- Generating device configuration from structured data.
    
- Collecting existing device configuration.
    
- Converting CLI configuration into structured Ansible data.
    

Unlike `merged`, `replaced`, and `deleted`, these states **do not directly modify the device configuration**.

---

# State Options

|State|Purpose|
|---|---|
|`rendered`|Converts structured Ansible data into Cisco IOS CLI commands.|
|`gathered`|Retrieves the current device configuration and returns it in structured format.|
|`parsed`|Converts provided CLI configuration text into structured Ansible data.|

---

# 1. `state: rendered`

## Purpose

The `rendered` state generates the equivalent Cisco IOS CLI configuration from the YAML data provided in the playbook.

It **does not connect to the device** and **does not make any changes**.

It is useful for:

- Generating configuration templates.
    
- Reviewing commands before deployment.
    
- Creating configuration files.
    

---

## Example

```yaml
- name: Render hostname configuration
  cisco.ios.ios_hostname:
    config:
      hostname: CSR1
    state: rendered
```

---

## Output

Ansible converts:

```yaml
config:
  hostname: CSR1
```

into:

```text
hostname CSR1
```

Example output:

```yaml
rendered:
  - hostname CSR1
```

---

## Workflow

```text
YAML Data
    |
    ▼
Resource Module
    |
    ▼
Cisco IOS CLI Commands
```

No device connection is required.

---

# 2. `state: gathered`

## Purpose

The `gathered` state retrieves the current configuration from the Cisco device and returns it in structured Ansible format.

It is useful for:

- Auditing.
    
- Backup purposes.
    
- Documentation.
    
- Configuration analysis.
    

---

## Example

```yaml
- name: Gather hostname configuration
  cisco.ios.ios_hostname:
    state: gathered
```

---

## Device Configuration

Cisco device:

```text

```

---

## Gathered Output

Ansible returns:

```yaml

  hostname: CSR1
```

---

## Workflow

```text
Cisco IOS Device
        |
        ▼
Current Configuration
        |
        ▼
Resource Module
        |
        ▼
Structured YAML Data
```

---

# 3. `state: parsed`

## Purpose

The `parsed` state converts raw Cisco IOS configuration text into structured Ansible data.

Unlike `gathered`, it does not retrieve configuration from the device.

The configuration is provided manually using the `running_config` parameter.

---

## Example

```yaml
- name: Parse hostname configuration
  cisco.ios.ios_hostname:

    running_config: |
      hostname CSR1

    state: parsed
```

---

## Input

Raw Cisco configuration:

```text
hostname CSR1
```

---

## Parsed Output

Structured format:

```yaml
parsed:
  hostname: CSR1
```

---

## Workflow

```text
CLI Configuration File
          |
          ▼
Resource Module
          |
          ▼
Structured YAML Data
```

# Summary

The resource module states provide a complete configuration lifecycle:

- **Gather** existing device configuration using `gathered`.
    
- **Parse** offline configuration files using `parsed`.
    
- **Render** structured data into CLI commands using `rendered`.
    
- **Deploy** changes using `merged`, `replaced`, or `overridden`.
    

These states make Ansible network automation more predictable, reusable, and suitable for large-scale configuration management.
