# Understanding `loop_control` in Ansible

## What is `loop_control`?

`loop_control` is used to **customize how a loop behaves** in Ansible. It allows you to:

- Rename the default loop variable (`item`).
    
- Track the current iteration using an index.
    
- Display a more meaningful label during task execution.
    
- Improve the readability of playbook output.
    

---

# Example Playbook

```yaml
---
- name: Register variables with loop
  hosts: R1
  gather_facts: false

  vars:
    interfaces:
      - name: GigabitEthernet3/0
        ip: 192.168.75.11
        subnet: 255.255.255.0

      - name: GigabitEthernet4/0
        ip: 192.168.76.11
        subnet: 255.255.255.0

  tasks:

    - name: Fetch interface traffic and assign to a variable
      cisco.ios.ios_command:
        commands:
          - "show interface {{ item.name }} | include rate"
      register: interface_rate
      loop: "{{ interfaces }}"

    - name: Loop over the registered variables
      ansible.builtin.debug:
        msg: "{{ interface.stdout[0] }}"
      loop: "{{ interface_rate.results }}"
      loop_control:
        loop_var: interface
        index_var: index
        label: "The item {{ index + 1 }} : Traffic on interface {{ interface.item.name }}"
```

---

# Why Use `loop_control`?

Without `loop_control`, Ansible automatically creates a variable named `item`.

Example:

```yaml
- debug:
    msg: "{{ item.stdout[0] }}"
  loop: "{{ interface_rate.results }}"
```

Here, `item` represents each element in `interface_rate.results`.

Although this works, using `item` becomes confusing when:

- Nested loops are used.
    
- Registered variables already contain an `item` field.
    
- Playbooks become larger and more complex.
    

Using `loop_control` makes the code much easier to read.

---

# `loop_var`

```yaml
loop_control:
  loop_var: interface
```

This changes the loop variable name from the default `item` to `interface`.

Without `loop_var`:

```yaml
msg: "{{ item.stdout[0] }}"
```

With `loop_var`:

```yaml
msg: "{{ interface.stdout[0] }}"
```

Now it is immediately clear that the current loop item represents an interface.

---

# `index_var`

```yaml
loop_control:
  index_var: index
```

Creates a variable named `index` that stores the current loop number.

The index starts at **0**.

|Iteration|index|
|---|--:|
|First|0|
|Second|1|
|Third|2|

If you want numbering to begin with 1, simply add 1:

```yaml
{{ index + 1 }}
```

Example output:

```text
1
2
```

instead of

```text
0
1
```

---

# `label`

```yaml
label: "The item {{ index + 1 }} : Traffic on interface {{ interface.item.name }}"
```

The `label` option changes what Ansible displays during task execution.

Normally, Ansible prints the complete loop item, which can be very large.

For example, without `label` you may see:

```text
ok: [R1] => (item={
  "stdout": [...],
  "item": {
      "name": "GigabitEthernet3/0",
      "ip": "192.168.75.11",
      "subnet": "255.255.255.0"
  },
  "changed": false,
  ...
})
```

This output can be difficult to read.

With `label`:

```yaml
label: "The item {{ index + 1 }} : Traffic on interface {{ interface.item.name }}"
```

Ansible displays:

```text
ok: [R1] => (item=The item 1 : Traffic on interface GigabitEthernet3/0)

ok: [R1] => (item=The item 2 : Traffic on interface GigabitEthernet4/0)
```

This makes the playbook output much cleaner and easier to understand.

---

# Understanding `interface.item.name`

This can be confusing the first time you see it.

The registered variable (`interface_rate.results`) stores each iteration like this:

```yaml
results:
  - item:
      name: GigabitEthernet3/0
      ip: 192.168.75.11
      subnet: 255.255.255.0
    stdout:
      - "5 minute input rate 1000 bits/sec"

  - item:
      name: GigabitEthernet4/0
      ip: 192.168.76.11
      subnet: 255.255.255.0
    stdout:
      - "5 minute input rate 2500 bits/sec"
```

When you loop over `interface_rate.results`, each loop iteration is stored in the variable `interface` (because of `loop_var`).

So:

```yaml
interface
```

contains:

```yaml
item:
  name: GigabitEthernet3/0
stdout:
  - "5 minute input rate 1000 bits/sec"
```

Therefore:

```yaml
interface.item.name
```

means:

- `interface` → Current loop result.
    
- `item` → Original interface dictionary used in the first loop.
    
- `name` → Interface name.
    

---

# Accessing Different Values

|Expression|Description|
|---|---|
|`interface.stdout[0]`|Command output for the current interface.|
|`interface.stdout_lines`|Output split into lines.|
|`interface.item.name`|Original interface name.|
|`interface.item.ip`|Original interface IP address.|
|`interface.item.subnet`|Original interface subnet mask.|
|`index`|Current loop index (starts at 0).|
|`index + 1`|Human-friendly numbering (starts at 1).|

# Example Output

Suppose the router returns:

```text
GigabitEthernet3/0
5 minute input rate 1000 bits/sec

GigabitEthernet4/0
5 minute input rate 2500 bits/sec
```

The task output becomes:

```text
TASK [Loop over the registered variables]

ok: [R1] => (item=The item 1 : Traffic on interface GigabitEthernet3/0) =>
    msg: 5 minute input rate 1000 bits/sec

ok: [R1] => (item=The item 2 : Traffic on interface GigabitEthernet4/0) =>
    msg: 5 minute input rate 2500 bits/sec
```

# Summary

|`loop_control` Option|Purpose|
|---|---|
|`loop_var`|Renames the default loop variable (`item`) to a more descriptive name.|
|`index_var`|Creates a variable containing the current loop index (starting at 0).|
|`label`|Displays a custom, readable label for each loop iteration in the task output.|

### Key Benefits

- Improves playbook readability.
    
- Avoids confusion when working with nested loops or registered variables.
    
- Produces cleaner task output.
    
- Makes debugging easier by displaying meaningful labels instead of the full loop item.
