# `cisco.ios.ios_config`

## What is `ios_config`?

The `cisco.ios.ios_config` module is used to **configure Cisco IOS devices**.

Unlike `ios_command`, which only executes operational (EXEC mode) commands such as `show version` or `show ip interface brief`, `ios_config` enters **global configuration mode** and applies configuration changes.

### Comparison

|Module|Purpose|Configuration Mode|
|---|---|---|
|`ios_command`|Executes show/EXEC commands|❌ No|
|`ios_config`|Configures the device|✅ Yes|

---

# Basic Syntax

```yaml
- name: Configure Cisco Device
  cisco.ios.ios_config:
    lines:
      - hostname R1
      - ip name-server 8.8.8.8
      - ntp server 1.1.1.1
```

---

# Understanding `lines`

The **`lines`** parameter contains one or more IOS configuration commands.

Each line is executed as if you typed it under **Global Configuration Mode**.

Example:

```yaml
lines:
  - hostname R1
  - ip name-server 8.8.8.8
  - ntp server 1.1.1.1
```

Equivalent CLI:

```text
R1# configure terminal
R1(config)# hostname R1
R1(config)# ip name-server 8.8.8.8
R1(config)# ntp server 1.1.1.1
R1(config)# end
```

# Idempotency

## What is Idempotency?

**Idempotency** means:

> Running the same playbook multiple times results in the same device state without making unnecessary changes.

This is one of Ansible's core principles.

---

## Example 1

Current configuration:

```text
hostname R1
```

Playbook:

```yaml
lines:
  - hostname R1
```

### First Run

Configuration changes:

```text
hostname R1
```

Result:

```text
changed = true
```

### Second Run

Ansible compares the desired configuration with the current configuration.

It sees:

```text
Current:
hostname R1

Desired:
hostname R1
```

Nothing is different.

Result:

```text
changed = false
```

No command is sent because the device is already in the desired state.

---

## Example 2

Current configuration:

```text
hostname Router
```

Playbook:

```yaml
lines:
  - hostname R1
```

Comparison:

```text
Current  -> hostname Router
Desired  -> hostname R1
```

They differ, so Ansible sends:

```text
hostname R1
```

Result:

```text
changed = true
```

---

# Why Idempotency Matters

Without idempotency:

Every run would reconfigure the device, even when nothing has changed.

With idempotency:

```text
Run 1
↓
Configuration Updated
↓
changed = true

Run 2
↓
No Difference Found
↓
changed = false

Run 3
↓
No Difference Found
↓
changed = false
```

Benefits include:

- Faster playbook execution.
    
- Avoids unnecessary configuration commands.
    
- Produces predictable results.
    
- Makes repeated automation runs safe.
    

---

# How `ios_config` Achieves Idempotency

Before applying configuration, the module compares the **desired configuration** (from `lines`) with the **running configuration**.

If they match:

```text
Do Nothing
```

If they differ:

```text
Send Only the Required Commands
```

This comparison is what makes `ios_config` idempotent for standard configuration lines.

---

# Example

Current router:

```text
hostname R1
ip name-server 8.8.8.8
```

Playbook:

```yaml
lines:
  - hostname R1
  - ip name-server 8.8.8.8
  - ntp server 1.1.1.1
```

Comparison:

|Configuration|Exists?|
|---|---|
|hostname R1|✅|
|ip name-server 8.8.8.8|✅|
|ntp server 1.1.1.1|❌|

Only this command is sent:

```text
ntp server 1.1.1.1
```

# Best Practices

- Use variables instead of hardcoded values for reusable playbooks.
    
- Group related configuration commands together in `lines`.
    
- Verify variables like `dns_server` and `ntp_server` are defined in your inventory or variable files before running the playbook.
    
- Remember that `lines` is intended for configuration mode commands. Use `cisco.ios.ios_command` for operational commands such as `show` commands.

# Key Takeaways

- `ios_config` configures Cisco IOS devices by entering configuration mode.
    
- `lines` is an ordered list of configuration commands to apply.
    
- Variables (for example, `{{ inventory_hostname }}`) make the same playbook work across multiple devices.
    
- `ios_config` is **idempotent**: it compares the desired configuration with the current running configuration and only applies changes when needed.
    
- The `changed` status reflects whether the device configuration was actually modified.
